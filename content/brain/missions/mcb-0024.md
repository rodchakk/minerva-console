# MCB-0024 — Brain Desktop Extraction & Local-First Foundation

Assigned role: orchestrator / architecture
Assigned agent/model: unassigned
Human merge owner: Rudy

## Status

Planned — future-near mission. Do not start implementation until Rudy explicitly activates it.

## Purpose

Extract Minerva Core Brain from Minerva Console and establish it as an independent desktop-first, model-agnostic memory/context/workspace layer for Rudy.

Brain is not the primary AI chat surface. Rudy continues interacting primarily with GPT/ChatGPT, Claude when needed, and eventually a local model. Brain exists to preserve, organize, retrieve, and hand off context so those AIs can resume work without Rudy repeatedly rebuilding project history from memory.

## Product definition to preserve

Brain's primary jobs are:

- Persistent memory for Minerva projects, products, decisions, missions, pending work, sources, prompts, agent outputs, and approved knowledge.
- Context retrieval and packaging for GPT, Claude, Codex, and future local AI.
- Mission/workspace organization so ongoing work can be resumed accurately.
- Model-agnostic continuity: knowledge belongs to Brain, not to any one model or chat provider.
- A local work surface capable of understanding repositories, Git state, files, and developer tooling on Rudy's machine.
- Human-owned authority: Rudy remains the decision and merge owner.

A native Brain chat may exist later as a utility, but it is not the center of the product.

## Target architecture

Desktop-first, local-processing, cloud-persistence:

```text
Rudy
  |
  +--> GPT / ChatGPT
  +--> Claude
  +--> future local AI
            |
            v
      Minerva Brain
      Desktop App
      Windows + macOS
            |
      local runtime
      - filesystem
      - Git
      - repo awareness
      - context engine
      - mission tools
      - indexing/search
      - local workers/processes
            |
            v
      cloud persistence
      Postgres/Neon-class DB
      - memory
      - missions
      - decisions
      - projects
      - relationships
      - history
```

Cloud infrastructure should store durable data; routine Brain processing should occur locally where practical. The desktop app must not require Docker to remain running for normal use.

## Platform direction

- Desktop only for Brain itself.
- Windows and macOS are first-class targets.
- Electron is the preferred initial desktop shell because the existing Brain stack is TypeScript/React/Node and Electron provides local filesystem/process access with minimal stack expansion.
- No mobile Brain application is planned.
- Minerva Field may consume selected Brain-generated information in the future through a separate integration, but Brain itself remains desktop-oriented.

## Migration plan

### Phase 1 — Brain Extraction

- Create an independent `minerva-brain` repository.
- Move/copy the Brain-specific knowledge tree, mission system, scripts, types, and reusable UI from `minerva-console`.
- Remove dependencies on ENTRY/Console auth, shell, routes, and runtime.
- Preserve Git history/evidence where practical.
- Keep Minerva Console operational and remove Brain from it only after the independent Brain is validated.

### Phase 2 — Desktop Foundation

- Add Electron desktop shell.
- Support Windows and macOS from one codebase.
- Build a visual Brain interface around the existing domains:
  - Overview
  - Projects
  - Missions
  - Decisions
  - Memory
  - Context
  - Sources
  - Agents
  - Activity
  - System/Settings
- Add secure local filesystem/Git/process bridge.
- Allow configurable local workspaces such as `D:\\Dev` or `~/Dev`.
- Package an installable Windows build and define the macOS packaging path.

### Phase 3 — Persistent Brain

- Introduce a small cloud Postgres persistence layer (Neon or equivalent at implementation time).
- Cloud stores durable knowledge; it is not the primary process runtime.
- Keep the existing loader seam or equivalent so UI does not depend directly on storage implementation.
- Migrate approved Brain knowledge from Git-backed registries into structured persistence without discarding Git audit/history.
- Define offline/local cache and synchronization behavior.
- Protect against disk failure by keeping durable knowledge off-machine and recoverable on a replacement computer.

### Phase 4 — Context Bridge

- Turn the existing context-pack/export work into first-class Brain capabilities.
- Make project/mission/context retrieval easy for GPT, Claude, Codex, and future local models.
- Support scoped context packs rather than dumping the entire Brain.
- Provide a practical bridge for ChatGPT first; initial implementation may use GitHub-synced context exports if direct local integration is not yet appropriate.
- Preserve a future MCP/local bridge path without making MCP a prerequisite for the desktop MVP.
- Capture new decisions, mission state, and approved knowledge back into Brain through a reviewed workflow.

### Phase 5 — Hardening

- Installer/packaging.
- Application updates.
- Backup/sync health visibility.
- Credential storage.
- Error recovery.
- Database migration safety.
- Local cache recovery.
- Windows/macOS parity checks.
- Production-readiness review.

## Existing assets to reuse

The current Brain already provides useful building blocks and should not be rebuilt without reason:

- `content/brain/**`
- mission ledger
- decisions/projects/prompts/agents/inbox registries
- Markdown reader and relations
- search/tag index
- inbox capture + promotion workflow
- mission loop/protocol/role contracts
- `brain:export-context`
- scoped context packs
- loop state snapshot
- guardrails and review evals
- the typed Brain content loader seam

## Non-goals for the first desktop foundation

- Building a new chatbot to replace GPT/Claude.
- Mobile/iOS/Android Brain app.
- Autonomous agents with unrestricted authority.
- Rebuilding ENTRY, Seshat, or Minerva Console inside Brain.
- Running production product databases locally.
- Requiring Docker, Redis, Kubernetes, or a multi-service server stack for normal desktop use.
- Deep local-model integration before the desktop/context foundation is stable.

3. New repo name and ownership.
4. Electron desktop architecture.

8. Context bridge plan for ChatGPT/Claude/local AI.
9. No regression to Minerva Console or product operations.
10. Rudy approves the execution brief before code migration starts.

## Relationship to MCB-0023

MCB-0023 remains a separate local-model triage experiment. MCB-0024 is the broader platform/extraction mission and does not require local-model integration to succeed. Any deeper local-AI integration should follow the desktop/context architecture rather than drive it.
