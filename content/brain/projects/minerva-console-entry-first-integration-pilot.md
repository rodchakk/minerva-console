# MINERVA-CONSOLE-ENTRY-PILOT-001 — ENTRY-first Manual Integration Pilot

## Status

Planned — part of `MINERVA-CONSOLE-001`.

## Purpose

ENTRY will be the **first real product connected through the new Minerva Control Center product-integration flow**.

Although ENTRY already lives natively inside Minerva Console, the Control Center must treat ENTRY as the first reference implementation for the product registry, module metadata, connection/setup UX, status rendering, and integration contract. This pilot is how Minerva validates that adding a product to Console is understandable and repeatable before connecting another Minerva system.

## Core rule

Product integration in V1 is **manual and guided**.

`Add Product` must not pretend to auto-discover, auto-configure, or autonomously modify another application. The user deliberately creates the product record, receives the exact integration instructions, performs the required implementation/configuration with a human or AI coding agent, enters the required values manually, and then asks Console to verify the connection.

Conceptual flow:

```text
Add Product
    ↓
Choose product type / connection mode
    ↓
Enter basic product metadata
    ↓
Console generates product-specific setup instructions
    ↓
Human gives instructions to Codex / Claude / other implementer
    ↓
Implement required endpoint/module contract
    ↓
Return to Console
    ↓
Enter connection values manually
    ↓
Test connection
    ↓
Review detected/returned overview data
    ↓
Activate product in Control Center
```

There is no requirement for automatic provisioning in V1.

## ENTRY is the first test case

ENTRY must be used to prove the complete V1 integration experience before the pattern is considered ready for another product.

The implementation should use ENTRY to validate:

- product/module registry shape;
- Add Product/setup UX;
- instructions generated by Console;
- manual configuration fields;
- connection test behavior;
- product-card rendering;
- operational / development / error / locked states where applicable;
- navigation from Control Center into the existing ENTRY module;
- no regression to existing ENTRY Operations, Communities, Users, Messages, Tickets, Settings, community, unit, or resident flows.

Because ENTRY is already native to the repository, the pilot should avoid inventing a fake external architecture solely to imitate an external product. Use the minimum real seam necessary to validate the same setup concepts that a future product will follow.

## Add Product — guided manual setup

The first version of `Add Product` should behave like a small setup wizard rather than a one-click connector.

### Step 1 — Product identity

Suggested fields:

```text
Product name
Slug
Description
Icon / mark
Owner / team
Environment
Status
```

### Step 2 — Product type

```text
Native Minerva module
External / connected product
```

### Step 3 — Connection mode

V1 modes:

```text
Link only
Overview API
Native module
```

`Full integration` may be shown only as a future/disabled concept if useful; do not implement a universal full-integration framework in this pilot.

### Step 4 — Generate instructions

After enough metadata is entered, Console should provide product-specific implementation guidance.

Preferred actions:

- `View setup instructions`
- `Copy AI instructions`
- `Download MINERVA_CONNECTOR.md` / Integration Kit when available

The generated instructions should include values already entered in the wizard so the implementer does not have to reinterpret a generic document.

Example context supplied to the implementation agent:

```text
Product: ENTRY
Slug: entry
Integration type: Native module / Overview contract
Expected Console route: /products/entry
Allowed data: aggregate operational summary only where needed
Brain access: none through this connector
Recurring-cost rule: no new paid service
Protected modules: do not modify Brain unless separately scoped
```

## Manual connection values

The user must be able to return to the setup flow and enter/edit the actual connection values manually.

Depending on connection mode, fields may include:

```text
Admin / module URL
Overview endpoint
Health endpoint (optional / future)
API token or connector credential (only if needed)
Environment
Connection label
```

Requirements:

- optional fields stay optional;
- secrets/credentials are server-only and must never be rendered back in plaintext after storage;
- no credentials are required for Link-only products;
- do not force a credential model on native modules that do not need one;
- all values should be editable through an explicit integration/settings surface rather than code changes when reasonably possible.

## Test Connection

`Test connection` is a deliberate user action.

For an Overview API product it should, at minimum:

1. validate that the configured URL is structurally acceptable;
2. make a safe read-only request;
3. validate the response against the V1 overview contract;
4. show a human-readable result;
5. never write to the connected product;
6. never send the response to Brain.

Example successful result:

```text
Connection successful
Status: operational
Users: 247
Alerts: 0
Last activity: 8m ago
```

Example failure states should explain what the builder needs to fix, such as unreachable endpoint, unauthorized connector, invalid response shape, or missing required field.

Do not create autonomous retries, background monitors, cron jobs, or paid observability to support this test.

## Activation / publish step

A product should not be treated as fully connected merely because its record was created.

Suggested setup states:

```text
draft
instructions_ready
configuration_needed
ready_to_test
connected
error
```

For a simple Link-only product, `connected` may mean the URL/config was accepted without a network probe.

For an Overview API product, `connected` should require a successful manual `Test connection`.

The product card may then appear in the active Control Center product list with only capabilities that are genuinely available.

## Integration Kit relationship

The separate future `minerva-console-integration-kit` repository remains the clean, shareable source for generic integration instructions and examples.

The Console setup wizard should eventually consume or mirror that contract and personalize it for the product currently being added.

V1 implementation may start with an in-repo Markdown template or generated instruction block if creating the separate repository would unnecessarily enlarge the first Control Center PR. The architecture must keep the generic documentation separable from private ENTRY and Brain code.

## No-cost / no-automation boundary

The manual setup choice is intentional.

V1 must not add:

- automatic product discovery;
- automatic repository modification;
- AI API calls from Console;
- connector provisioning services;
- background connection polling;
- cron-based health checks;
- event buses;
- paid monitoring;
- product-data replication.

The Console provides the contract, stores the approved configuration, tests it on demand, and renders the result.

## Brain boundary

Nothing about adding or testing a product grants the connector access to Brain.

The integration flow must not forward product response payloads to Brain or create Brain knowledge automatically from product data.

Brain may separately document the Minerva implementation work itself — for example that ENTRY passed the integration pilot — but that is a human/mission workflow, not connector ingestion.

## Acceptance criteria — ENTRY pilot

The pilot is successful when:

1. `Add Product` provides a clear manual, guided setup path rather than automatic integration.
2. ENTRY is the first real system used to validate the product/module integration pattern.
3. The setup flow can present product-specific implementation instructions suitable for handing directly to an AI coding agent.
4. Relevant connection/configuration values can be entered and edited manually from Console.
5. A deliberate `Test connection` path validates supported read-only integrations without background infrastructure.
6. ENTRY appears correctly in Control Center and opens the existing native ENTRY console.
7. Existing ENTRY operations are not duplicated or regressed.
8. The pilot does not require new recurring infrastructure or AI cost.
9. Product data used for connection testing does not flow into Brain.
10. The resulting pattern is documented well enough that the next Minerva product can follow the same guided procedure.

## Implementation relationship

This is an implementation addendum to:

- `MINERVA-CONSOLE-001 — Minerva Console Control Center Foundation`
- `DEC-0008 — Minerva Console is the modular web home for Minerva products`

If implementation discovers that ENTRY's native nature makes a specific external-connector step inapplicable, record the difference explicitly rather than fabricating a fake dependency. The goal is to prove the **setup contract and user experience**, not to force all products to have identical internals.
